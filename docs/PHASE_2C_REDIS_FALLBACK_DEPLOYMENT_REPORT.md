# تقرير تصحيح النشر — بديل جلسات TiDB عند غياب Redis

## السبب الفعلي

فشل النشر لم يكن خطأً في واجهة T3 + I1. كان API يرفض البدء في `NODE_ENV=production` عندما لا يجد `REDIS_URL`، ثم كانت الحاوية تنهي التنفيذ قبل أن تستجيب لفحص TCP. سبب ذلك أن مرحلة Phase 2A جعلت Redis شرطًا خارجيًا صريحًا للجلسات، بينما بيئة النشر الحالية لا توفر عنوان Redis ولم يزوّد المالك خدمة Redis.

## التصحيح المنفذ

تمت إزالة شرط بدء الإنتاج الذي كان يرفض غياب `REDIS_URL`، **من دون** استخدام ذاكرة الحاوية للجلسات. أصبح `SessionService` يعمل بمسارين متوافقين:

| حالة الإعداد | مخزن الجلسات | السلوك الأمني |
|---|---|---|
| `REDIS_URL` متوفر | Redis | يحتفظ بمسار Redis القائم. |
| `REDIS_URL` غير متوفر | TiDB `server_sessions` | جلسات server-side دائمة عبر الحاويات، رمز CSRF، مهلة خمول، حد مطلق، logout، وإلغاء جميع جلسات المستخدم. |

أضيف جدول `server_sessions` وmigration إضافية `20260824170000_add_server_sessions_fallback`. التغيير لا يعدل أي جدول أعمال أو صلاحيات أو API route أو منطق CSRF/RBAC؛ فقط طبقة تخزين الجلسات. تم تطبيق جدول migration على قاعدة المشروع عبر قناة قاعدة البيانات ثم تم تسجيل migration في Prisma.

## التحقق الفعلي

| الفحص | النتيجة |
|---|---|
| اختبار بديل TiDB المستهدف | PASS — إنشاء/قراءة/إبطال/إلغاء جلسات المستخدم دون `REDIS_URL`. |
| اختبار الأمن والجلسات | PASS — 10/10 في الاختبارات المستهدفة. |
| الانحدار الكامل | PASS — **7 ملفات / 32 اختبارًا**. |
| TypeScript وبناء الإنتاج | PASS. |
| بدء الإنتاج دون `REDIS_URL` | PASS — `dist/index.js` بدأ على منفذ الاستضافة، و`/api/v1/health/ready` أعاد `{"status":"ready","database":"ok","sessionStore":"tidb"}`. |

تظهر تحذيرات حجم bundle ومعلومة `baseline-browser-mapping` أثناء البناء، لكنها لا تمنع البناء أو بدء الخدمة. لا يحتاج هذا التصحيح إلى Redis وهمي أو حساب Redis خارجي.

## حدود وحالة النشر

هذا التصحيح يحل سبب خروج الحاوية الظاهر في سجل النشر. نقطة الاستعادة التالية ستنشر النسخة الجديدة تلقائيًا. يبقى فحص Prisma migration history في قاعدة التطوير الحالية متأثرًا بتاريخ Phase 2A القديم المحفوظ (canonical baseline مقابل تاريخ migrations قديم)، وهو ليس مسار بدء الحاوية ولا سبب هذا الفشل؛ migration الجديدة موجودة في المصدر ومطبقة في قاعدة المشروع.

## تأكيد النشر المنشور

تم التحقق من سجلات الإنتاج بعد النشر: سجّل Nest بدء التطبيق بنجاح، وتم تسجيل كل مسارات `auth` و`health` و`foundation`، ثم ظهرت رسالة `api_started` على المنفذ `3000`. لا يحتوي سجل الحاوية الجديد على `REDIS_URL must be configured outside development` أو `api_boot_failure`. لذلك **تمت معالجة سبب فشل النشر الذي أبلغ عنه المالك**.
